# Self Prompt – Падение контейнера videochat_api при открытии Swagger UI

## Цель
Обеспечить стабильную работу сервиса videochat_api в dev-компоузе: открытие Swagger UI по `http://127.0.0.1:8000/docs` не должно завершать контейнер и останавливать uvicorn.

## Контекст
- Приложение построено на FastAPI, в `main.py` при старте поднимаются подключения к БД/Redis и PresenceService через lifespan, а затем FastAPI оборачивается в `socketio.ASGIApp` для совмещения REST и Socket.IO. 【F:apps/api/videochat_api/main.py†L17-L68】
- Dev-компоуз запускает контейнер `videochat_api` из `python:3.11-slim`, прогоняя `pip install -e .[dev]`, миграции и `uvicorn ... --reload`, поэтому сбой рабочего процесса приводит к мгновенной остановке контейнера. 【F:infra/docker/docker-compose.dev.yml†L43-L63】
- README подчёркивает, что Swagger UI (`/docs`) используется для ручной проверки API и должен работать в dev-режиме. 【F:apps/api/README.md†L83-L96】
- Тестовый стенд собирает чистый FastAPI-приложение без Socket.IO-обёртки, поэтому падение, возникающее только в реальном ASGI-стеке, сейчас не покрыто автотестами. 【F:apps/api/tests/conftest.py†L95-L119】

## Проблема
При запуске `docker compose -f infra/docker/docker-compose.dev.yml up -d` сервис успешно поднимается, но первый же заход на `http://127.0.0.1:8000/docs` приводит к завершению процесса `uvicorn` и контейнер `videochat_api` пропадает из `docker ps`. Необходимо найти и устранить причину краша, чтобы Swagger UI больше не обрушивал backend.

## Предлагаемое решение
1. Воспроизвести проблему и изучить `docker logs videochat_api`, чтобы зафиксировать стек-трейс и убедиться, что падение инициируется на стороне ASGI-приложения (ожидаемый кандидат — некорректная прокладка lifespan/`scope['app']` между `socketio.ASGIApp` и FastAPI). 【F:apps/api/videochat_api/main.py†L53-L68】
2. Реализовать собственный тонкий адаптер вместо прямого `ASGIApp`, который:
   - корректно проксирует события `lifespan` во внутреннее FastAPI-приложение, чтобы не терялись `redis` и `presence_service` в `app.state`;
   - для HTTP-запросов заменяет `scope['app']` на исходный FastAPI, чтобы внутренняя логика (включая `Request.app.state` и автоматическую генерацию OpenAPI/Swagger) работала так же, как в тестах;
   - продолжает делегировать Socket.IO-пути (`/socket.io`) в `socketio.AsyncServer`.
   В результате экспортируемый `app` остаётся совместимым с uvicorn, но перестаёт ронять процесс при обращении к Swagger. 【F:apps/api/videochat_api/main.py†L17-L68】
3. Обновить `tests/conftest.py`, чтобы фикстура `app` использовала тот же фабричный метод (`create_fastapi_app`) и адаптер, что и продакшен, тем самым гарантируя воспроизводимость подобных ошибок в CI. 【F:apps/api/tests/conftest.py†L95-L113】【F:apps/api/videochat_api/main.py†L30-L56】
4. Добавить регрессионный тест, который поднимает приложение под новым адаптером и выполняет `GET /docs` и `GET /openapi.json`, убеждаясь, что запросы завершаются 200 OK и приложение остаётся живым (например, через `AsyncClient` и контроль `client.app`).
5. После исправления обновить README раздел «Проверка работоспособности», если потребуется упомянуть новый способ запуска или ограничения (например, отказ от `--reload` не потребуется, если адаптер исправит корневую проблему). 【F:apps/api/README.md†L83-L96】

## Проверка
- Локально: `docker compose -f infra/docker/docker-compose.dev.yml up -d`, переход на `http://127.0.0.1:8000/docs`, затем `docker ps` — контейнер `videochat_api` должен оставаться в статусе `Up`.
- Автотесты: `pytest` (убедиться, что новый регрессионный тест и существующие сценарии проходят).

## Риски и открытые вопросы
- Нужно убедиться, что переработанный адаптер не ломает WebSocket-трафик и совместим с существующей логикой `videochat_api.websocket.server`.
- Возможна дополнительная настройка hot-reload (`uvicorn --reload`), если адаптер будет вмешиваться в наблюдение файлов — потребуется проверить, что live-reload продолжает работать.
- Стоит проверить, что ресурсы (Redis/БД) корректно закрываются при остановке контейнера после переноса lifecycle-логики.
