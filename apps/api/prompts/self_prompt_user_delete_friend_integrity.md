# Self Prompt — IntegrityError при удалении пользователя

## Цель
Устранить падение `DELETE /users/{id}` при наличии дружеских связей и гарантировать, что удаление аккаунта очищает связанные заявки без нарушения ограничений БД.

## Контекст
- API обслуживает пользователей, дружбу и комнаты через FastAPI; удаление пользователя реализовано в `api/endpoints/users.py` и предварительно отзывает сессии. 【F:apps/api/videochat_api/api/endpoints/users.py†L134-L214】
- ORM-модель дружбы `FriendRelationship` хранит `requester_id` и `addressee_id` со строгим `NOT NULL` и `ForeignKey(..., ondelete="CASCADE")`, но связана с `User` через `relationship(..., backref=...)` без специальных настроек. 【F:apps/api/videochat_api/models/friend.py†L1-L45】
- Текущие тесты удалений в `tests/test_users.py` не покрывают сценарий с друзьями, поэтому ошибка не воспроизводится автоматически. 【F:apps/api/tests/test_users.py†L1-L141】
- Архитектурные заметки подчёркивают использование каскадных удалений и важность синхронизации Pydantic/ORM. 【F:apps/api/README.md†L15-L112】【F:apps/api/knowledge/friends.md†L1-L17】

## Проблема
При удалении пользователя, у которого есть принятые дружеские связи, SQLAlchemy пытается обновить связанные объекты: устанавливает `addressee_id=NULL`, что нарушает `NOT NULL` и приводит к `IntegrityError` (`asyncpg.exceptions.NotNullViolationError`). Это воспроизводится при `DELETE /users/{id}` после принятой заявки в друзья.

## Предлагаемое решение
1. Настроить связи `FriendRelationship.requester` и `FriendRelationship.addressee` с `passive_deletes=True` (как на стороне связи, так и в `backref`), чтобы ORM не отправлял `UPDATE` при удалении пользователя и полагался на каскад `ON DELETE CASCADE`.
2. Добавить интеграционный тест в `tests/test_users.py`, который создаёт дружбу, удаляет участника и убеждается в удалении связанных записей без 500.
3. Убедиться, что дополнительные изменения не требуются в Pydantic-схемах и миграциях (модель БД уже корректно настроена).

## Проверка
- Запустить `pytest`, чтобы убедиться в прохождении существующих тестов и нового сценария удаления с дружбой.
- При ручной проверке повторить: создать заявку в друзья, принять её, удалить одного из участников через Swagger или HTTP-клиент — ответ должен быть `204`, а в БД не должно остаться записей дружбы.

## Риски и открытые вопросы
- Нужно убедиться, что `passive_deletes` не нарушит обратные связи (например, ленивую загрузку дружеских списков) и что каскадные удаления в БД доступны во всех окружениях.
- Если в будущем появятся дополнительные ограничения или soft-delete, потребуется переоценить стратегию очистки зависимостей.
