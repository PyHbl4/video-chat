# Self Prompt — логирование в файл

## Цель
Настроить централизованное логирование FastAPI/Socket.IO приложения `videochat_api` в файл с ротацией по размеру, чтобы журналы можно было читать прямо из репозитория.

## Контекст
- Архитектура описана в `apps/api/README.md`: единое FastAPI-приложение с Socket.IO через адаптер `SocketIOFastAPIApp`, lifespan открывает PostgreSQL и Redis, хранит `PresenceService` в `app.state`.
- Дополнительные детали в `apps/api/knowledge/*`: аутентификация через cookie/JWT и Redis rate limiting, дружба и комнаты транслируются в Socket.IO, presence работает поверх Redis (`presence.md`).
- Точка входа — `videochat_api/main.py`: создаёт FastAPI-приложение, настраивает CORS, подключает роутеры, оборачивает в `create_socketio_fastapi_app`, запускается через Uvicorn.
- Логирование разбросано по модулям (`dependencies.py`, `api/endpoints/auth.py`, `websocket/server.py`), но отсутствует централизованная конфигурация для вывода в файл.
- Git игнорирует все `*.log`, поэтому для целевого файла нужно исключение.

## Проблема
Требование заказчика — писать все логи приложения в файл в каталоге проекта и автоматически ротировать его при достижении критического размера. Сейчас Uvicorn и собственные логгеры пишут только в stdout, файлы в репозитории не появляются, а `.gitignore` блокирует добавление `.log` файлов.

## Предлагаемое решение
1. Создать модуль `videochat_api/logging_config.py` с функцией `configure_logging()`, которая:
   - Определяет путь `apps/api/videochat_api.log`.
   - Настраивает `RotatingFileHandler` (например, 10 МБ и 5 резервных копий для покрытия 1–2 суток логов при типичной нагрузке).
   - Подключает обработчик к root-логгеру и логгерам `uvicorn.error`/`uvicorn.access`, выравнивая уровни на `INFO` и сохраняя формат `'%(asctime)s [%(levelname)s] %(name)s: %(message)s'`.
   - Избегает дублирования обработчиков при повторных импортах (важно для hot-reload).
2. Импортировать и вызвать `configure_logging()` в `videochat_api/main.py` до создания FastAPI-приложения, чтобы конфигурация применялась при каждом запуске (включая `uvicorn --reload`).
3. Обновить `.gitignore`, добавив исключение `!apps/api/videochat_api.log`, чтобы файл можно было зафиксировать в репозитории при необходимости.
4. При желании описать поведение в документации (например, в README), если заказчик ожидает явного упоминания.

## Проверка
- Запустить `pytest` из `apps/api`, чтобы убедиться в отсутствии регрессий.
- Локально стартовать `uvicorn videochat_api.main:app` и отправить запросы, проверив, что `apps/api/videochat_api.log` создаётся и пополняется, а при превышении размера появляются файлы `videochat_api.log.1`, `videochat_api.log.2` и т.д.

## Риски и открытые вопросы
- Размер 10 МБ условен: при повышенной нагрузке журнал может ротироваться чаще, чем раз в 1–2 дня; при необходимости параметр стоит вынести в настройки.
- В много-процессном деплое (несколько Uvicorn workers) общий файловый обработчик может привести к состязаниям; для таких сценариев может потребоваться сторонняя система логирования.
- Репозиторий может разрастаться из-за хранения логов — стоит договориться о политике коммитов и очистки.
