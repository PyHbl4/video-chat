# Self Prompt — удаление пользователя

## Цель
Реализовать REST-эндпоинт, который позволяет удалять пользователя по идентификатору. Запрос должен завершаться успешно только если его инициирует сам владелец учётной записи или администратор, после чего связанные сущности и активные сессии должны быть корректно очищены.

## Контекст
- FastAPI-приложение собирает маршруты в `videochat_api/api/routes.py`, а пользовательские обработчики находятся в `api/endpoints/users.py`. 【F:apps/api/videochat_api/api/routes.py†L1-L15】【F:apps/api/videochat_api/api/endpoints/users.py†L1-L133】
- Аутентификация строится на зависимостях `get_current_user` и `get_current_admin_user`, которые выдают текущего пользователя и валидируют права администратора. Они используются в существующих эндпоинтах и обеспечивают ревокацию сессий для заблокированных аккаунтов. 【F:apps/api/videochat_api/dependencies.py†L49-L108】
- Пользовательская модель связана с устройствами, сессиями, дружбой и участием в комнатах через каскадные связи `ondelete="CASCADE"`/`delete-orphan`, что упрощает очистку зависимых данных при удалении пользователя. 【F:apps/api/videochat_api/models/user.py†L13-L32】【F:apps/api/videochat_api/models/friend.py†L21-L45】【F:apps/api/videochat_api/models/device.py†L16-L47】【F:apps/api/videochat_api/models/session.py†L13-L43】【F:apps/api/videochat_api/models/room.py†L19-L77】
- Менеджер сессий предоставляет метод `revoke_user_sessions`, который помечает все активные сессии пользователя отзывными и обнуляет связанные токены/устройства. Его нужно вызвать перед удалением, чтобы клиентские токены перестали работать. 【F:apps/api/videochat_api/auth/session.py†L199-L232】
- Тесты для пользовательских сценариев находятся в `tests/test_users.py`; они используют HTTP-клиент и фабрику пользователей, поэтому сюда же логично добавить проверки нового поведения. 【F:apps/api/tests/test_users.py†L1-L91】【F:apps/api/tests/conftest.py†L90-L152】

## Проблема
В модуле `api/endpoints/users.py` отсутствует обработчик `DELETE /users/{user_id}`. Сейчас нет возможности удалить аккаунт ни администратору, ни самому пользователю: роутер предоставляет только список пользователей и поиск. Требование задачи — ограничить удаление владельцем либо администратором — не реализовано, что блокирует сценарии деактивации и GDPR-удаления.

## Предлагаемое решение
1. Добавить в `api/endpoints/users.py` новый маршрут `@router.delete("/{user_id}")` со статусом `204 No Content`.
2. В обработчике парсить `user_id` как целое, извлекать цель через сессию БД (`AsyncSession`). При некорректном ID возвращать `400`, при отсутствии пользователя — `404`.
3. Авторизовать запрос через `get_current_user`:
   - Если текущий пользователь — администратор (`is_admin`), разрешить удаление любого пользователя.
   - В противном случае требовать совпадение `current_user.id` и `target.id`, иначе отвечать `403 Forbidden`.
4. Перед удалением вызвать `session_manager.revoke_user_sessions(db, target.id)` и закоммитить результат, чтобы активные web/JWT-сессии и устройства лишились токенов.
5. Удалить объект пользователя вызовом `await db.delete(target)` и `await db.commit()`; каскадные ограничения в моделях очистят связанные записи.
6. Вернуть пустой ответ со статусом `204`. Для консистентности можно дополнительно `await db.flush()` перед коммитом, если потребуется.
7. Покрыть логику тестами в `tests/test_users.py`: кейсы на удаление самим пользователем, удаление администратором, запрет удаления чужого аккаунта обычным пользователем и отсутствие пользователя.

## Проверка
- Запустить `pytest` — он покрывает HTTP-сценарии и убедится, что новые тесты проходят. 【F:apps/api/README.md†L87-L101】
- При необходимости провести ручную проверку через Swagger UI (`DELETE /users/{id}`) после авторизации, удостоверившись, что сессия аннулирована.

## Риски и открытые вопросы
- Удаление активного инициатора комнаты приведёт к каскадному удалению записей, но в Redis могут остаться устаревшие ключи presence/room. Сейчас сервис их не чистит; возможен техдолг по синхронизации Redis.
- В отсутствии дополнительного подтверждения (например, пароля) удаление владельцем может быть случайным, однако это выходит за рамки задачи.
- Если администратор удаляет самого себя, все его активные сессии закроются, и последующие админ-действия станут недоступны; следует задокументировать это поведение при необходимости.
