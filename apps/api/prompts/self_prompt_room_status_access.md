# Self Prompt — ограничение доступа к статусу комнаты

## Цель
Обновить эндпоинт `GET /rooms/{room_id}` и связанные сервисы так, чтобы статус комнаты получали только администраторы и пользователи, непосредственно добавленные в комнату (инициатор, приглашённый через `target_user_id`, участники), а прочие получали отказ в доступе.

## Контекст
- Приложение `apps/api` — FastAPI+Socket.IO сервис, описанный в README: комнаты управляются через `RoomService`, а администрирование использует зависимость `get_current_admin_user`. 【F:apps/api/README.md†L68-L116】【F:apps/api/videochat_api/api/endpoints/rooms.py†L1-L174】
- Инструкции AGENTS подчёркивают необходимость синхронизации логики, Redis и документации `knowledge/` и `prompts/` при изменении REST-эндпоинтов. 【F:apps/api/AGENTS.md†L1-L42】
- `RoomService.get_room_for_user` сейчас разрешает доступ друзьям инициатора, даже если они не участники. Документация по комнатам фиксирует текущее поведение («участник, инициатор или друг инициатора»). 【F:apps/api/videochat_api/services/rooms.py†L176-L205】【F:apps/api/knowledge/rooms.md†L11-L18】
- Тесты `tests/test_rooms.py` проверяют доступ приглашённого друга до фактического присоединения и 403 для постороннего пользователя, что придётся актуализировать под новую политику. 【F:apps/api/tests/test_rooms.py†L66-L122】

## Проблема
- Эндпоинт `/rooms/{room_id}` зависит от `get_current_user` и вызывает `RoomService.get_room_for_user`, который допускает любого друга инициатора. Это нарушает новое требование: посторонний друг, не добавленный в конкретную комнату, всё ещё получает статус (возврат 200). 【F:apps/api/videochat_api/api/endpoints/rooms.py†L143-L174】【F:apps/api/videochat_api/services/rooms.py†L176-L205】
- Документация в `knowledge/rooms.md` устарела: она описывает доступ для друзей инициатора, хотя по новой политике так быть не должно. 【F:apps/api/knowledge/rooms.md†L11-L18】

## Предлагаемое решение
- Расширить `RoomService.get_room_for_user`: добавить флаг администратора и ужесточить проверки — оставлять доступ только если пользователь админ (`user.is_admin`), инициатор, записан в `room.participants` или совпадает с `room.target_user_id` (для приглашённого, ещё не присоединившегося). Исключить проверку дружбы.
- В `GET /rooms/{room_id}` определять `is_admin` по `current_user.is_admin`; для админов вызывать сервис с обходом ограничений, для остальных — стандартную проверку. При необходимости можно пробросить `allow_admin=True`, чтобы не дублировать `_get_room` в эндпоинте.
- Обновить `knowledge/rooms.md`, удалив упоминание про «друга инициатора» и описав новую модель доступа.
- Дополнить/исправить тесты `tests/test_rooms.py`: 
  - Обновить сценарий приглашённого пользователя, чтобы подтверждалось разрешение благодаря `target_user_id`.
  - Добавить новый тест для администратора, подтверждающий свободный доступ к любым комнатам.
  - Расширить негативные кейсы, убеждаясь, что друг инициатора без приглашения получает 403.
- Убедиться, что сервис продолжает корректно обрабатывать Redis-кэш (логика `_touch_cache`/`_persist_cache` не меняется).

## Проверка
- Запустить `pytest` в `apps/api`, чтобы убедиться в прохождении тестов комнат и смежных сценариев.
- По желанию: ручная проверка через Swagger или `httpx`, создавая комнату, проверяя доступ инициатора, приглашённого, администратора и постороннего пользователя.

## Риски и открытые вопросы
- Клиентские приложения, полагающиеся на прежний доступ «друзей инициатора», перестанут получать статус комнаты; требуется согласование и обновление фронтенда.
- Необходимо уточнить, должен ли приглашённый пользователь иметь доступ к статусу до присоединения. Решение опирается на поле `target_user_id`; если требуется другая модель (например, явная запись участника при приглашении), придётся расширять сервис.
