# Self Prompt — Перевод пользователей на enum-роль

## Цель
Перевести хранение административных прав с булевого флага `is_admin` на перечисление ролей, чтобы поддерживать несколько уровней доступа и подготовить основу для расширенного RBAC.

## Контекст
- FastAPI-приложение `videochat_api` использует SQLAlchemy-модели в каталоге `videochat_api/models` и Pydantic-схемы в `videochat_api/schemas`.【F:apps/api/AGENTS.md†L1-L35】
- Модель `User` сейчас содержит колонку `is_admin` с типом `Boolean`, а признак блокировки хранится отдельно в `is_blocked`.【F:apps/api/videochat_api/models/user.py†L6-L34】
- Pydantic-схемы `UserResponse` и `UserListItem` сериализуют поле администратора под ключом `isAdmin`, что используется в REST-ответах `/auth/me` и `/users`.【F:apps/api/videochat_api/schemas/auth.py†L31-L48】【F:apps/api/videochat_api/schemas/users.py†L1-L57】
- Существующие миграции управляются через Alembic; тесты запускаются командой `pytest` из каталога `apps/api` и опираются на модели/схемы по умолчанию.【F:apps/api/AGENTS.md†L36-L43】

## Проблема
- Флаг `is_admin` позволяет фиксировать только два состояния (админ/не админ) и не масштабируется до ролей модератора, пользователя и т. д.
- Отсутствует централизованное поле `role`, из-за чего будущие зависимости FastAPI не смогут проверять тонкие права доступа.
- REST-ответы и тесты жёстко завязаны на поле `isAdmin`, что затрудняет переход на систему ролей.

## Предлагаемое решение
1. Добавить перечисление ролей (`user`, `moderator`, `admin`) в `videochat_api/models/user.py` и заменить булевый `is_admin` на колонку `role` с типом `Enum`, значением по умолчанию `user`.
2. Подготовить Alembic-миграцию: создать enum-тип, добавить колонку `role`, скопировать значения из `is_admin` (`True` → `admin`, `False` → `user`), после чего удалить колонку `is_admin` и enum почистить в downgrade.
3. Обновить Pydantic-схемы `UserResponse` и `UserListItem`, чтобы они возвращали `role` (с алиасом `role`) вместо `isAdmin`, сохранив обратную совместимость по возможности через временную поддержку чтения `isAdmin`.
4. Переписать фабрики/фикстуры пользователей в тестах на новое поле `role` и убедиться, что создаваемые пользователи получают `role="user"` по умолчанию.
5. Проследить, чтобы сериализация и доступ к данным на фронтенд-контракты отражали новое поле (обновить документацию/knowledge при необходимости).

## Проверка
- Выполнить `pytest` в каталоге `apps/api`, убедившись в прохождении существующих тестов.
- Ручной smoke-тест: зарегистрировать пользователя, убедиться, что `/auth/me` возвращает `role="user"`, а ранее админские пользователи отображаются как `role="admin"`.

## Риски и открытые вопросы
- Фронтенд и внешние клиенты могут ожидать булевое поле `isAdmin`; необходимо проверить контракты и при необходимости добавить временную совместимость.
- Неправильная миграция данных может обнулить права существующих администраторов; важно корректно перенести значения `is_admin=True`.
- Требуется оценить, не используют ли другие части кода прямой доступ к `is_admin`; поиск по репозиторию обязателен перед удалением поля.
