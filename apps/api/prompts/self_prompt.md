# Self Prompt – Rooms status access for invited friend

## Цель
Обеспечить, чтобы приглашённый в комнату пользователь мог получить статус видеокомнаты через `GET /rooms/{room_id}` и наблюдать изменения состояний (waiting → active → ending/closed), не сталкиваясь с 403.

## Контекст
- Приложение FastAPI живёт в `videochat_api.main`, а комнаты реализованы REST-эндпоинтом `api/endpoints/rooms.py` и сервисом `services/rooms.py`. 【F:apps/api/videochat_api/main.py†L17-L62】【F:apps/api/videochat_api/api/endpoints/rooms.py†L1-L164】【F:apps/api/videochat_api/services/rooms.py†L1-L220】
- README предписывает ручную проверку комнат: второй пользователь должен вызвать `GET /rooms/{room_id}` и увидеть смену статуса после подключения обоих участников. 【F:apps/api/README.md†L82-L112】
- Knowledge база по комнатам описывает, что статус получают участники; нужно синхронизировать документацию с фактическим поведением. 【F:apps/api/knowledge/rooms.md†L1-L84】
- Тест `test_room_status_requires_membership` ожидает 403 для приглашённого друга, закрепляя некорректное поведение. 【F:apps/api/tests/test_rooms.py†L33-L69】

## Проблема
При создании комнаты сервис добавляет только инициатора в `room_participants`. В методе `RoomService.get_room_for_user` доступ выдаётся исключительно, если пользователь найден среди участников. Приглашённый друг, который ещё не подключился по WebSocket, не проходит эту проверку и получает `RoomForbiddenError("Нет доступа к комнате")`. Из-за этого ручная проверка из README невозможна, а приглашённый клиент не может отслеживать статус до подключения.

## Предлагаемое решение
1. В `RoomService.get_room_for_user` дополнительно разрешать доступ приглашённому другу, проверяя дружбу инициатора через `get_friend_user_ids`. Возвращать комнату, если `user_id` совпадает с инициатором (safety) или содержится в списке друзей, иначе выбрасывать 403.
2. Обновить тест `test_room_status_requires_membership`, переименовать и ожидать 200 для приглашённого друга, удостоверившись, что статус `waiting` и в участниках присутствует инициатор.
3. Добавить новый тест, который подтверждает сохранение 403 для постороннего пользователя без дружбы, чтобы зафиксировать защиту от доступа чужих пользователей.
4. Актуализировать knowledge (`knowledge/rooms.md`), уточнив, что статус доступен инициатору и приглашённому другу до фактического подключения.
5. При необходимости проверить, что сериализация ответа не ломается и Socket.IO события не требуют правок.

## Проверка
- Запустить `pytest` в `apps/api`. Перед запуском убедиться, что установлены dev-зависимости (`pip install -e .[dev]`), иначе упадёт по отсутствию `httpx`.
- Ручной сценарий: создать комнату, авторизоваться под приглашённым другом и выполнить `GET /rooms/{room_id}` — ожидать 200 и статус `waiting`; после подключения по Socket.IO статус должен перейти в `active`.

## Риски и открытые вопросы
- Любой друг инициатора, получивший UUID комнаты, теперь сможет посмотреть её статус; случай утечки ID низковероятен, но стоит документировать.
- Необходимо следить, чтобы кеш в Redis и уведомления о приглашении продолжали работать при обновлении логики доступа.
