## Контекст

- Имеем утверждённую UX-стратегию с акцентом на трёхколоночный каркас, адаптивность и богатые сценарии звонков.
- В веб-клиенте сейчас реализован только раздел "Друзья" без полноценных роутов, состояний звонков и поисковой шапки.
- Админ-панель представляет собой страницу-заглушку после авторизации; нужно привести её к единому visual language и подготовить каркас под метрики.
- UI-кит `@video-chat/ui` уже подключён, но токены и темы ещё не соответствуют утверждённому брендингу (бирюзовый акцент, мягкие тени, радиусы 14px).

## Текущее состояние и основные гэпы

### Web-приложение

- **Навигация**: один маршрут `/app` с FriendsAppPage, отсутствуют секции Chats/Calls/Inbox/Settings/Search, нет нижней навигации для mobile.
- **Каркас**: Sidebar из `@video-chat/ui` используется, но нет колоночного layout для списка/контента, отсутствуют placeholders для будущих страниц.
- **Состояния**: Skeleton и пустые состояния покрывают только список друзей, нет унификации loading/error/incoming call.
- **Звонки**: отсутствует отдельный маршрут `/call/[roomId]`, нет компонентов сетки, тулбара, панелей устройств, баннеров слабой сети.
- **Уведомления**: toasts реализованы через кастомные хуки для друзей, но нет глобального провайдера sonner и политики отображения.
- **Темизация**: глобальные CSS-переменные отличаются от утверждённых токенов (нет бирюзового `#10B981`, другие тени и радиусы).
- **Доступность**: фокус-стили есть на уровне shadcn, но нет глобальной проверки шорткатов, aria-live, поддержка `prefers-reduced-motion` не реализована.
- **Производительность**: нет виртуализации списков, debounce поиска 350ms вместо 300ms, нет ленивой загрузки тяжёлых модалей (не критично, но нужно учесть).

### Admin-приложение

- **Маршруты**: только `/` с приветственным card, отсутствуют разделы пользователей, статистики, логи.
- **UI-структура**: нет sidebar/topbar, не используется общий App Shell, токены такие же как в вебе (см. выше).
- **Состояния/доступность**: нет шаблонов для таблиц/панелей, фокус и клавиатурная навигация не проверены.

## План работ (итерации и крупные эпики)

### Эпик A. Дизайн-система и токены (общий для web/admin)

1. **Токены темы**: привести `globals.css` в web и admin к палитре из дополнения (фон, текст, бирюзовый акцент, радиусы 14px, мягкие тени). Вынести общие токены в пакет (напр. `packages/ui` или `packages/design-tokens`).
2. **Переключение тем**: реализовать контекст и контролы для светлой/тёмной темы, учесть системный режим и синхронизацию через `localStorage` (MVP).
3. **Документация**: описать токены и тему в `docs/ui-ux` или `README`, добавить инструкции по кастомизации (brand.json).
4. **Проверка контрастности и prefers-reduced-motion**: добавить CSS-правила/utility для сокращённой анимации, протестировать контрастность акцентных элементов.

### Эпик B. Каркас и навигация web-приложения

1. **App Shell**: расширить текущий `AppShell` до трёхколоночного layout (sidebar + список + контент), добавить адаптивное переключение для tablet/mobile.
2. **Маршруты**: создать `app/(dashboard)/friends`, `.../chats`, `.../calls`, `.../inbox`, `.../settings`, `.../search`; подготовить страницы-заглушки с пустыми состояниями.
3. **Нижняя навигация (mobile)**: внедрить tab-bar с иконками и состояниями, сохранить контекст при переходах.
4. **Breadcrumbs/Topbar**: продумать заголовок контента, быстрые CTA (создать чат, начать звонок).
5. **Keyboard навигация**: описать и реализовать Tab-порядок, шорткаты (M, V, S, E, P, A) через глобальный listener.

### Эпик C. Сценарии звонков и экран Call

1. **Маршрут `/call/[roomId]`**: создать страницу с состояниями `connecting`, `active`, `reconnecting`, `ended`.
2. **Сетка участников**: реализовать компонент тайлов по правилам 1×1, 1×2, 2×2, 2×3, поддержка закрепления.
3. **Toolbar**: кнопки mute/camera/screen/end/more, отображение статусов, хоткеи.
4. **Панели устройств**: модалка выбора микрофона/камеры/динамика, превью, тест звука.
5. **Баннеры**: слабая сеть, параллельный звонок, только аудио.
6. **Incoming call flow**: toast + модальное окно с действиями (принять, отклонить, завершить текущий и принять).
7. **События и уведомления**: интеграция с sonner, ограничение до 2 активных уведомлений, таймауты ≤3 сек.

### Эпик D. Списки, состояния и поиск

1. **Унификация Loading/Empty/Error**: вынести компоненты `LoadingState`, `EmptyState`, `ErrorBanner` с CTA и кнопкой Retry.
2. **Скелеты**: расширить skeleton’ы на Friends, Chats, Calls.
3. **Поиск**: добавить UI инпута в Friends/Chats + глобальный `/search` хедер с табами (Users/Chats/Files) на будущее.
4. **Inbox**: подготовить карточки заявок/пропущенных событий.
5. **Виртуализация**: рассмотреть `react-virtualized` или `@tanstack/react-virtual` для длинных списков.
6. **Debounce**: настроить 300 мс и вынос в хук.

### Эпик E. Настройки и локальные предпочтения

1. **Settings страница**: секции профиль, устройства, качество связи, темы, приватность.
2. **Локальное хранение**: `localStorage` для темы, последнего таба, mute, состояния сайдбара.
3. **Подготовка к user_preferences**: определить интерфейсы, выделить сервис синхронизации (пока stub).

### Эпик F. Admin-приложение

1. **App Layout**: внедрить общий shell с sidebar (разделы: Dashboard, Users, Calls, Settings), поддержка тем и токенов.
2. **Карты и таблицы-заглушки**: создать placeholder-компоненты (карточка метрик, таблица пользователей) с пустыми состояниями.
3. **Доступность**: проверить фокус, добавить клавиатурную навигацию и шорткаты (например, `G` для перехода к пользователям).
4. **Документация**: добавить раздел в README/admin о UX-принципах и будущих модулях.

### Эпик G. Документация и тесты

1. **Тест-планы**: описать сценарии тестирования (desktop/mobile, звонок, тема, уведомления) в `docs/ui-ux`.
2. **Storybook/Playground (опционально)**: рассмотреть запуск storybook для компонентов UI.
3. **Accessibility тесты**: добавить автоматические проверки (axe) в CI или локальный скрипт.

## Предварительная оценка трудоёмкости

- Эпик A: 3–4 недели (включая рефакторинг токенов и переключение тем для двух приложений).
- Эпик B: 4–6 недель (много адаптивной верстки и маршрутизации, зависит от дизайна финальных страниц).
- Эпик C: 6–8 недель (сложность звонкового UI, состояния, модалки, интеграция уведомлений).
- Эпик D: 3–4 недели (унификация состояний, поиск, виртуализация).
- Эпик E: 2–3 недели (настройки + локальные предпочтения).
- Эпик F: 2 недели (админка проще, но нужно заложить каркас).
- Эпик G: 1–2 недели (документация и тест-планы, можно параллелить).
- Общая оценка: 5–6 месяцев суммарно при небольшом фронтенд-тиме (1–2 человека) с частичным параллелизмом.

## Вопросы и уточнения

1. **Приоритет эпиков**: какие разделы важнее закрыть к ближайшему релизу (Friends/Calls/Settings или, возможно, Search)?
2. **Call backend**: планируется ли встраивание реальной медиалогики параллельно, чтобы синхронизировать API и UI? Нам нужен список событий/сигналинга для моков.
3. **Уведомления**: можем ли мы подключить сторонние звуки для входящего звонка, или придерживаемся "без звуков" кроме звонков? Нужны ли собственные аудио-файлы?
4. **Admin метрики**: есть ли предпочтения по первому набору данных (онлайн пользователи, нагрузка, ошибки)? Это повлияет на структуру каркаса.
5. **Брендирование**: хотим ли мы закладывать `brand.json` уже сейчас или отложить до отдельной задачи?
6. **Анимации логотипа**: есть ли готовые референсы/ожидания по анимации `main-logo.tsx`, чтобы не расходиться с видением?
7. **Совместное тестирование**: кто будет участвовать в пилотных UX-тестах? Нужно понять, как планировать обратную связь на этапе готовности каркаса.

## Заметки

- Для трёхколоночного layout можно опираться на existing `Sidebar` + дополнительный `ResizablePanel` (если хотим ширину подстраивать).
- Стоит сразу заложить сервис состояния для звонков (store + hooks), чтобы другие команды могли подключить реальную WebRTC-логику.
- Возможно, имеет смысл выделить подзадачи по каждой теме в `.tasks/backlog` после получения ответов на вопросы.
